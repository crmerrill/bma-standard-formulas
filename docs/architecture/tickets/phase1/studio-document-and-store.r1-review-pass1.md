# R1 Review (Pass 1) — `studio-document-and-store` decomposition

**Reviewer**: gpt-5.5-extra-high (R1 tier; separate invocation; read-only; cross-family from gemini-3.1-pro D1 decomposer + Claude-family parent + future Claude implementers)
**Date**: 2026-06-01
**Decomposition under review**: `docs/architecture/tickets/phase1/studio-document-and-store.md`
**Verdict**: RETURN-FOR-REVISION

## Summary

The five-ticket envelope captures the right backbone (deps → DocumentSession → compile → patch lifecycle → autosave) and correctly walls off out-of-scope artifacts (sidecar, validation engine, AI pipeline, panes). However, the decomposition does not meet the irvc-1 precision bar: AC specificity is roughly 30–50% of irvc-1's, several master-contract obligations from the plan are unrepresented (diagnostics slot in store, ephemeral-session creation API, three-way-merge conflict UX on Apply, multi-session preview render assertion), and two foundational mechanisms are silently inconsistent with the landed `irvc-4` surface — most importantly that `POST /deals/{id}/commit` as merged does NOT accept a working-tree payload from the client and commits only to `main`, so `sds-5`'s autosave and ephemeral-branch commit story cannot be implemented against the existing endpoint without a new ticket or an amendment to irvc. The Python↔TS round-trip harness in `sds-3` and the zundo-per-session architecture in `sds-2` are left ambiguous in ways that will block the implementer mid-flight. Fold-back is required before T1 authoring opens.

## Findings

### Blocking

1. **(sds-5, AC 1; sds-4, AC 2)** — `POST /deals/{deal_id}/commit` as landed in `irvc-4` does NOT accept a working-tree payload from the client. Inspecting `src/bma_cfengine_app/api/routers/deals.py` L1007–L1030: the endpoint reads the current `deal.json` from `main` HEAD (`service.show(head_sha, "deal.json")`) and re-commits *that* payload — it is effectively a metadata-only commit. `CommitRequest` carries only `author`, `message`, `parent_sha`, `force`; there is no field for the new IR payload. Furthermore the endpoint hard-codes the target ref to `main` (no `branch` argument). The decomposition assumes (a) `sds-5` autosave can call `POST /commit` with the active session's `working_tree` against the active session's branch, and (b) `sds-4` Apply's pre-merge path commits the ephemeral session's working tree to its own branch. Neither is possible against the merged surface. **Proposed fix**: add a new ticket `sds-0-irvc-commit-endpoint-extension` (Layer 0, depends on `irvc-4`; or fold into a corrigendum to irvc-4) that extends `CommitRequest` with `payload: dict[str, Any]` (or `payload_b64: str`) and `branch: str = "main"`, updates `commit_deal_endpoint` to write the supplied payload to the supplied branch (with `parent_sha` validated against that branch's tip), and pin the AC to "405-style refuse on `branch == 'main'` from any ephemeral-session caller is NOT required — the endpoint is symmetric across branches; per-branch policy enforcement lives in the store, not the API." Make `sds-4` and `sds-5` depend on this new ticket.

2. **(sds-2, missing AC; sds-4, AC 1)** — No ticket creates an ephemeral `DocumentSession`. The plan (L362) requires "the system creates an ephemeral branch from the current `main` HEAD AND creates an ephemeral `DocumentSession` bound to that branch with `base_sha = main HEAD at turn open`, `working_tree = in-memory store seeded from base_sha`." `sds-4`'s `previewEphemeralSession(sessionId)` action only flips `ui_role` on an *existing* session; nothing wires up session creation. Without a `createEphemeralSession({ branch_name, base_sha })` (or analogous) action that (i) calls `POST /deals/{id}/branches`, (ii) instantiates the session record, (iii) seeds `working_tree` by loading `deal.json` at `base_sha`, the Apply/Discard flow has no entry point and the AC 1/AC 2 tests cannot be authored. **Proposed fix**: add an AC to `sds-2` for `createEphemeralSession(opts: { branch_name: BranchName; base_sha: string; ui_role: 'preview' }) → sessionId`, with a test that asserts (a) `POST /deals/{id}/branches` is invoked, (b) a new `DocumentSession` is added to `state.sessions` with `working_tree` seeded from `GET /deals/{id}/show?sha={base_sha}&path=deal.json`, (c) the main session is untouched. Move the API-call assertions to `sds-4` if you want to keep `sds-2` API-free; in that case `sds-2` defines the session-record shape + state mutation, and `sds-4` adds the HTTP call.

### Critical

1. **(sds-3, AC 6)** — Python↔TS round-trip harness mechanism is unspecified. The AC says the test "loads the fixture, compiles the store, and asserts the output is byte-identical to the post-migration `deal.json`," but the test file path `tests/ui_integration/test_canonical_roundtrip.py` is Python while `compileToIR` is TypeScript. There is no statement of how Python invokes the TS compile, or vice versa. Three plausible mechanisms exist: (a) Python emits `<fixture>.canonical.json` at fixture-build time and a Vitest test reads them + compares against a fresh TS-side compile; (b) Vitest shells out to `python -m bma_cfengine_app.tools.dump_canonical` at test time; (c) a CI step pre-emits both sides into artifacts and a Python comparator job diffs. Each has different repo/CI implications and different fixture-author obligations. The decomposer must pick one. **Proposed fix**: pin AC 6 to mechanism (a): "A Python fixture-build helper at `tests/ui_integration/build_canonical_fixtures.py` (invoked via a `pytest` fixture or a Makefile target `make canonical-fixtures`) iterates `tests/fixtures/*/deal.json`, runs the post-migration load + `model_dump_json(indent=2)` path, and writes `<fixture>/deal.canonical.json` checked into the repo. The Vitest test `compile.roundtrip.test.ts` (NOT a Python file) reads each `<fixture>/deal.json`, runs `compileToIR`, and asserts byte-identity to `<fixture>/deal.canonical.json`. A CI step regenerates the canonical fixtures and fails if they drift from the committed bytes." Re-home the test file from `tests/ui_integration/test_canonical_roundtrip.py` to `src/bma_cfengine_app/ui/src/features/deals/store/compile.roundtrip.test.ts` and add the fixture-build helper as a sibling file in the Files-affected list.

2. **(sds-3, AC 2–4)** — "Pydantic field declaration order" has no propagation mechanism into TypeScript. TS does not have access to Pydantic's runtime metadata; without an explicit field-order manifest the TS `compileToIR` will silently diverge whenever a Python-side field is added/reordered. **Proposed fix**: add an AC: "A field-order manifest at `src/bma_standard_formulas/deals/schemas/field_order.json` is emitted by a Python script (`scripts/emit_field_order.py`) that introspects `DealDefinition` + every nested model and writes a nested `{ModelName: [field_names_in_declaration_order]}` map. `compileToIR` imports this manifest (vendored to `ui/src/features/deals/field_order.json` at build time via a Vite plugin or a pre-commit hook) and uses it to serialize fields in declaration order. A CI guard runs `scripts/emit_field_order.py --check` and fails if the manifest drifts from the live Pydantic models. Drift between the Python and vendored TS copies fails CI." This is the only mechanism that satisfies "byte-identical to `model_dump_json`" without re-implementing Pydantic's introspection in TS.

3. **(sds-4, AC 2)** — Apply on an advanced `main` (i.e., user kept editing during the ephemeral session's lifetime) is undefined. The plan (L364) explicitly requires three-way merge handling: "(a) attempts to fast-forward `main` from the ephemeral session's `base_sha` to current `main` HEAD; if `main` has advanced, runs the application-level typed field merge." The merged `POST /deals/{id}/merge` endpoint returns `GitMergeResult(status: 'success' | 'conflict', sha, diagnostic)` — the conflict branch is real and the decomposition must define what the store does with it. `sds-4` AC 2 currently asserts only the success path. **Proposed fix**: split AC 2 into AC 2a (success: status='success' → update main session base_sha + working_tree, write ONE zundo entry, delete ephemeral session) and AC 2b (conflict: status='conflict' → leave main session unchanged, leave ephemeral session intact, set `state.applyConflict = { sessionId, diagnostic: MergeConflictPayload }`, surface a conflict-resolution UI state). Add a Vitest test that uses a mocked `POST /merge` returning `status='conflict'` with a valid `MergeConflictPayload` and asserts the store state.

4. **(sds-1 / sds-2 / sds-3, missing AC)** — Diagnostics slot in the store is missing entirely. The plan (L356) requires "Every action on the active session... emits diagnostics scoped to the session," and the field-class projection matrix (L473) explicitly lists "Compiled diagnostics + run state" as a store-resident field class. None of the five tickets adds a `diagnostics: DiagnosticPayload[]` (or `Map<diagnostic_id, DiagnosticPayload>`) to the session, and no AC pins the diagnostic-merge semantics (replace-all per validation pass vs. accumulate). Downstream tickets (`validation-engine` for the TS worker registry, the panes for jump-to-source) cannot bind to a missing slot. **Proposed fix**: add an AC to `sds-2`: "`DocumentSession.diagnostics: DiagnosticPayload[]` is included in the type and initialized to `[]`. A typed action `setDiagnostics(sessionId, DiagnosticPayload[])` replaces the slot atomically. A test asserts the slot exists, replaces correctly, and is per-session (setting on session A does not mutate session B)." Cite the TS structural mirror of `DiagnosticPayload` (planned in `vpc-3`, but a placeholder type alias `import type { DiagnosticPayload } from './diagnostics-types'` with the same six-field shape from `irvc-2`'s `MergeConflictPayload` is acceptable here; the parity contract is `validation-engine`'s job).

5. **(sds-4, AC 2)** — "Writes exactly ONE zundo entry to the main session" is not assertable without a mechanism choice. zundo records state diffs in response to mutations; "exactly one" depends on how the Apply mutation is batched. If the implementer does (a) `setBaseSha(...)` then (b) `setWorkingTree(...)` then (c) `deleteSession(...)`, zundo records three entries unless explicitly paused. **Proposed fix**: pin the mechanism in AC 2: "The Apply mutation is wrapped in `temporal.pause(); applyMutation; temporal.resume(); temporal.handleSet(state)` (or equivalent zundo API per the per-session architecture pick from sds-2) so that exactly one undo-stack entry is appended. The test asserts `temporal.getState().pastStates.length === N+1` where `N` is the count immediately before Apply, regardless of how many internal mutations the Apply path performs."

### Major

1. **(sds-2, AC 1)** — `DocumentSession` field types are not pinned. Compare to `irvc-1` AC 5 (slug grammar `[a-z0-9][a-z0-9-]{0,63}`) and `irvc-2` AC 5 (literal `entity_kind` set). `sds-2` AC 1 lists field names only. **Proposed fix**: pin "`DocumentSession` is exactly: `{ session_id: string; branch_name: BranchName; base_sha: string /* 40-char lowercase hex */; working_tree: DealState; validation_target: 'self'; commit_target: BranchName; zundo_history: TemporalState<DealState>; ui_role: 'primary' | 'preview'; diagnostics: DiagnosticPayload[] }`," where `BranchName` is a TS branded type matching the irvc-1 slug regex, and `DealState = DealDefinition` (the existing structural mirror in `ir-types.ts`).

2. **(sds-2, AC 4; Risk Note)** — Zundo-per-session implementation choice is left ambiguous; the Risk Note acknowledges this but does not sanction a pick. The two real options are (a) one zundo instance per session, stored as `sessions[id].zundo` (most direct, but requires `getZundo(sessionId)` access pattern in every undo/redo consumer), or (b) a single global temporal middleware with a custom `partialize` that scopes its diff window to the active session's working_tree (preserves single-store ergonomics but requires careful tracking of inter-session activeSessionId switches as non-undoable events). **Proposed fix**: sanction option (a) explicitly: "Each `DocumentSession` carries its own zundo instance created via `temporal(...)` middleware applied to a per-session sub-store. `useDealStore` holds `sessions: Record<string, { state: DocumentSession; temporal: TemporalState<DealState> }>`. Undo/redo dispatch routes to `sessions[activeSessionId].temporal`." This eliminates the cross-session-leak risk that option (b) introduces around `activeSessionId` swaps and is more directly testable.

3. **(sds-1, AC 3)** — Discriminated-union action shape lacks the type alias. **Proposed fix**: pin "`DealAction = AddBondAction | SetBondKindAction | SetRulePriorityAction` where `AddBondAction = { type: 'addBond'; payload: BondDef }`, `SetBondKindAction = { type: 'setBondKind'; payload: { bond_id: string; kind: BondKind } }`, `SetRulePriorityAction = { type: 'setRulePriority'; payload: { rule_id: string; priority: number } }`. The dispatcher signature is `dispatch(action: DealAction): void` with exhaustive switch enforced by `never`-guard." Match the precision of irvc-2 AC 5.

4. **(sds-1, AC 2)** — "Structurally mirrors `ir-types.ts`" is under-specified. **Proposed fix**: pin "the store's session.working_tree is typed as `DealState = DealDefinition` (the existing structural mirror in `src/bma_cfengine_app/ui/src/features/deals/ir-types.ts`); a test asserts that a fixture's `deal.json` parsed via `JSON.parse(...) as DealState` populates the working_tree without any field renames or shape transforms."

5. **(sds-3, AC 6)** — Fixture enumeration is missing. `irvc-3` AC 1 enumerates "`Migrate v1`, `Migrate v2`, ... in legacy version order"; `sds-3` says only "every fixture in `tests/fixtures/`." **Proposed fix**: pin the minimum fixture set the round-trip must cover: at least `fnr_2006_018`, `manual_two_class_v3`, `sample_deal_v1` (or whichever fixtures already exist in `tests/fixtures/` at decomposition-time — list them explicitly). Add an AC: "the fixture-build helper enumerates every directory under `tests/fixtures/` containing a `deal.json` file; a CI guard asserts that the count of `.canonical.json` files equals the count of fixture `deal.json` files." This makes the test self-extending without ambiguity.

6. **(sds-4, AC 4)** — 409 handling is missing the `force=true` retry path. The plan calls for "Reload / Save anyway" UX; the merged endpoint already accepts `force: bool = False`. **Proposed fix**: extend AC 4: "On 409 Conflict the store sets `conflictState = { kind: 'STALE_PARENT_SHA', head_sha: string, attempted_commit: { author, message, payload } }`. A `forceCommit(sessionId)` action retries the commit with `force=true`; a `reloadFromHead(sessionId)` action discards the pending commit and re-seeds `working_tree` from `head_sha`. Test plan covers both retry paths."

7. **(sds-3 / sds-4 / sds-5, Dependencies)** — Implicit irvc-4 dependency is not explicit on every ticket that needs git-backed endpoints. `sds-4` lists `ir-version-control-foundation`, but `sds-5` does not (despite calling `POST /deals/{id}/commit` directly per its own AC 1) and `sds-3` does not (but its round-trip helper consumes the post-migration deal.json, which is git-resident). **Proposed fix**: add `ir-version-control-foundation` (or, after Blocking #1's fold-back, the new commit-endpoint-extension ticket) to `sds-5`'s Dependencies. `sds-3`'s round-trip helper depends on the migration commit semantics from `irvc-3`; add `ir-version-control-foundation` to `sds-3`'s Dependencies as well.

8. **(sds-5, AC 3)** — sessionStorage recovery contract is under-specified. "If it is ahead of the loaded `base_sha`" — how is "ahead" determined? **Proposed fix**: pin "sessionStorage is keyed by `bma:draft:{deal_id}:{session_id}` and stores `{ working_tree: DealState; base_sha: string; saved_at: ISO8601 }`. On store init for a `(deal_id, session_id)` pair, the store reads the entry; if `entry.base_sha === currentBaseSha && JSON.stringify(entry.working_tree) !== JSON.stringify(currentWorkingTree)`, the store restores `entry.working_tree` and surfaces a 'Restored unsaved edits' diagnostic. If `entry.base_sha !== currentBaseSha`, the entry is discarded (the user has loaded a newer commit) and a diagnostic is surfaced for visibility." Test asserts both paths.

9. **(sds-3, Files affected)** — Test file path mixes runners. `compile.test.ts` is Vitest; `tests/ui_integration/test_canonical_roundtrip.py` is pytest. The cross-runtime split is not justified. **Proposed fix**: per Critical #1's pick, move the cross-language round-trip into a Vitest test (`compile.roundtrip.test.ts`) reading Python-emitted canonical artifacts. Drop the Python file from the Files-affected list. Add the canonical-emitter script (`scripts/emit_canonical_fixtures.py`) as a new Files-affected entry.

10. **(sds-2, missing AC)** — Multiple coexisting ephemeral sessions are not tested. Plan L367(e): "attempting a second proposal while a previous one is still previewed is allowed (multiple ephemeral sessions coexist)." **Proposed fix**: add an AC: "the store supports N coexisting non-primary sessions; a test creates 3 ephemeral sessions, dispatches an action to session 2, and asserts (a) sessions 1 and 3 working_trees are unchanged, (b) `Object.keys(state.sessions).length === 4` (1 primary + 3 ephemeral), (c) per-session zundo histories are independent."

### Minor

1. **(sds-1 / sds-2, Files affected)** — `useDealStore.ts` is modified in both tickets; `sds-2` restructures the shape from flat-fields to `sessions: Record<...>`. **Proposed fix**: consider whether `sds-1`'s initial scaffolding should *already* nest a `main` session record (with `ui_role: 'primary'`) so that `sds-2`'s diff is additive rather than restructuring. If yes, fold the session-record skeleton into `sds-1` AC 2 and trim `sds-2`'s churn surface. Either way, document the decision in `sds-1`'s scope paragraph.

2. **(sds-3, AC 5)** — "Compile step performs NO multi-target consolidation" is a negative assertion. **Proposed fix**: strengthen with a positive test: "given a fixture with at least one fragmented multi-target rule sequence (e.g., the IR contains rules A→X, A→Y, A→Z that a canonicalization linter would consolidate into one A→{X,Y,Z}), `compileToIR` emits the rules in fragmented form preserving authored order. The test references a specific fixture by name."

3. **(sds-5, AC 1)** — Debounce interval (2 seconds) is suggested but not pinned. **Proposed fix**: pin the interval in the AC: "a 2000ms debounce window (from the last typed action timestamp) triggers a single `POST /deals/{id}/commit`. The test uses fake timers and asserts (a) one commit is fired after 2000ms, (b) a burst of 5 actions within 1500ms produces exactly one commit." Add a `Risk Note` if 2000ms is open to tuning during implementation.

### Nit

1. **(Mermaid graph)** — Only the top-of-file header mentions the irvc dependency; the graph itself lacks the `irvc → sds-4` and `irvc → sds-5` edges (and `irvc → sds-3` if Major #7 is adopted). `ir-version-control-foundation`'s graph explicitly draws cross-todo edges (`vpc → irvc-2`); match that convention. **Proposed fix**: add the edges from `irvc` to `sds-3`, `sds-4`, `sds-5` in the mermaid diagram.

## What landed well

- Correct top-level sequencing: deps → DocumentSession → (compile ∥ patch lifecycle) → autosave. The fan-out at `sds-3`/`sds-4` and re-converge at `sds-5` is the right shape and matches the plan's data flow.
- Strong out-of-scope notes on every ticket: sidecar, AI pipeline, panes, validation engine, canonicalization linter, and the StudioSidecar are all explicitly walled off. The decomposer correctly recognized the Phase 0 B5/B6 walls.
- `sds-3` AC 5 ("compile performs NO canonicalization") is faithful to Phase 0 fold-back B6 and the plan's "compile is canonical serialization, not transformation" wording.
- `sds-4`'s `squash=true` reference on Apply aligns with the landed irvc-4 router behavior (per the irvc closure's Path B decision, ephemeral branches squash by default).
- Risk Notes on `sds-2` (zundo) and `sds-3` (round-trip weight) correctly flag the hardest implementation surfaces — even though both need to be turned into AC-level pins (per the findings above), the awareness is right.
- Test file paths follow the existing `src/bma_cfengine_app/ui/src/features/deals/...` convention and the `tests/...` orchestrator-side convention (modulo the cross-runtime mix flagged in Major #9).
